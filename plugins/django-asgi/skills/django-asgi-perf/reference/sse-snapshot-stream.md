# SSE: 스냅샷과 이어지는 스트림 사이에서 갱신을 잃거나 두 번 보내지 않기

## 상황

실시간 화면은 대개 이렇게 붙는다.
1. 접속하면 현재 상태 스냅샷을 보낸다.
2. 그 뒤 채널 메시지(pub/sub)를 이어 보낸다.
3. 1과 2가 겹치는 틈에 대해 거르기를 둔다.

이 틈은 두 방향으로 깨진다.
- **잃기:** 스냅샷을 읽은 뒤 구독하기 전에 생긴 갱신이 빠진다.
- **두 번:** 스냅샷에 이미 든 갱신이 스트림으로 한 번 더 온다.

## 규칙

1. **구독을 먼저 하고, 그다음에 스냅샷을 읽는다.** 반대 순서면 그 사이의 갱신을 잃는다. 구독해 둔 메시지는 스냅샷을 보낼 때까지 버퍼에 쌓는다.
2. **거르기는 단조 증가하는 순번으로 한다. 시각으로 하지 않는다.**
   - 발행할 때 채널마다 순번을 붙인다. Redis `INCR`, Redis Streams의 항목 id, DB 시퀀스, 이벤트 로그의 오프셋 같은 것이다.
   - 스냅샷은 「몇 번까지 반영했는지」를 함께 돌려준다.
   - 스트림은 그 번호 이하를 버리고 초과를 보낸다.
   - **시각은 겹친다.** 같은 밀리초, 「마지막 틱 시각」을 다는 논리 시계, 서버 사이 시계 어긋남이 그렇다. 그래서 `<=`로 거르면 같은 시각의 정당한 갱신을 잃고, `<`로 거르면 두 번 보낸다.
3. **재접속은 SSE `id:` 필드와 `Last-Event-ID`로 잇는다.** 순번을 `id:`로 보내 두면 브라우저가 다시 붙을 때 그 번호를 보낸다. 서버는 그 뒤부터 다시 보낸다. 다시 보낼 수 없을 만큼 지났으면 스냅샷을 새로 보낸다.
4. **id가 있는 항목(채팅 줄 등)은 항목 id로 거른다.**
5. **순번을 붙일 수 없을 때만 울타리를 쓴다.**
   - 방법: 스냅샷을 읽는 바로 그 자리에서 같은 채널에 표지 메시지(`{"type": "fence", "id": …}`)를 발행한다. 스트림은 표지 앞의 것만 버린다.
   - 조건: 스냅샷 읽기와 발행이 한 줄로 직렬화돼 있어야 한다(단일 처리 루프, 순서를 지키는 한 연결).
   - 표지를 못 받으면 예전 거르기로 돌아가고, 표지 자체는 화면에 보내지 않는다.

## 시험(백엔드, 빨강 먼저)

- 스냅샷을 읽은 직후, 같은 시각·같은 순간에 생긴 갱신이 클라이언트에 닿는다.
- 스냅샷에 이미 든 갱신은 두 번 오지 않는다. 거르기를 일부러 깨면 이 시험이 실패해야 한다.
- 재접속(`Last-Event-ID`) 뒤 빠진 것도 겹친 것도 없다.
- 시험 환경에서 시간을 멈추면 이 틈이 매번 드러난다. 시계를 멈춘 E2E에서 「접속 뒤 한 번 시간 감기」로 덮고 있다면 이 버그다.
