# 외부 보안 점검 (security-recon)

방어 목적의 점검 절차다. **1단계(인가·범위)를 통과하지 못하면 거기서 멈춘다.** 공격 페이로드·익스플로잇은 다루지 않는다 — 「무엇이 바깥에 보이는가」를 공개 도구로 재고, 막고, 다시 잰다.

명령 예시의 `<host>`·`<port>`·`<path>`·`<cidr>`는 자리표시자다. 실제 값은 점검 기록(비공개)에만 적는다.

## 1. 인가·범위 확인 — 문지기

아래가 **모두** 「예」가 아니면 점검을 시작하지 않고 사용자에게 무엇이 빠졌는지 말한 뒤 멈춘다.

- [ ] **서면 인가**가 있다(메일·계약·티켓 등 남는 형태). 인가자가 그 자산의 소유자거나 권한자다. 구두 허락만으로는 시작하지 않는다.
- [ ] **대상**이 주소·호스트 이름 단위로 정해져 있다. 「그 서버 근처」처럼 흐릿하면 묻는다.
- [ ] **제외 범위**가 정해져 있다(공유 호스팅·남의 테넌트·CDN·결제 등 제3자 서비스는 기본 제외).
- [ ] **시간대·연락처**: 언제 해도 되는지, 장애가 나면 누구에게 알리는지.
- [ ] 클라우드라면 그 클라우드의 **점검 정책**(사전 신고가 필요한지, 금지 항목)을 확인했다.
- [ ] **비파괴·저속** 원칙에 동의했다: 서비스 거부·대량 요청·데이터 변경·무차별 대입·취약점 공격 시도는 하지 않는다. 스캔은 속도를 낮추고(`nmap -T2` 안팎), 쓰기 요청은 보내지 않는다.

인가 범위를 넘는 것(다른 호스트, 내부망, 다른 계정의 데이터)이 보이면 **더 들어가지 말고 기록만 하고 보고한다.**

## 2. 외부 블랙박스 점검

**서로 다른 두 네트워크 지점**에서, 사설망·VPN·사내 프록시 **밖**의 공개 경로로 잰다. 한 지점만 보면 그 지점에만 열린 허용 규칙(사무실 대역, 관리 대역)을 「바깥에 열림」으로 착각하거나 반대로 놓친다. 예: 집·사무 회선 하나 + 다른 클라우드 리전의 임시 인스턴스 하나. 두 결과가 다르면 그 차이가 곧 허용 규칙의 모양이다.

결과는 표로 남긴다: 항목 / 지점 A / 지점 B / 기대 / 판정.

### 2.1 열린 포트

```bash
# 흔한 포트, 느리게, 서비스 이름만(버전 탐지·스크립트 없음)
nmap -Pn -T2 --top-ports 1000 <host>
# 전체 TCP — 시간이 걸린다. 인가 범위가 허락할 때만
nmap -Pn -T2 -p- <host>
# 열린 포트의 서비스 식별(비파괴 수준)
nmap -Pn -T2 -sV --version-light -p <port>,<port> <host>
# 도구가 없을 때 한 포트 확인
nc -zv -w 3 <host> <port>
```

점검 포인트:
- 바깥에 열려야 하는 것은 보통 웹(80·443)과 관리용 원격 접속 하나뿐이다. 그 밖의 것(DB·캐시·메시지 큐·관리 화면·모니터링·컨테이너 런타임 API·개발 서버)이 보이면 모두 이상으로 본다.
- 원격 접속은 키 인증만, 출발 대역 제한이 걸려 있는가.
- `filtered`와 `closed`의 차이: `filtered`는 앞단 방화벽이 버린 것, `closed`는 호스트까지 닿았는데 듣는 프로세스가 없는 것. `closed`는 바깥층이 열려 있다는 신호다.

### 2.2 TLS·인증서·보안 헤더

```bash
# 프로토콜 버전별 협상 가능 여부 (1.0·1.1은 실패해야 한다)
openssl s_client -connect <host>:443 -servername <host> -tls1_1 </dev/null
openssl s_client -connect <host>:443 -servername <host> -tls1_2 </dev/null
# 인증서 주체·발급자·만료·SAN
openssl s_client -connect <host>:443 -servername <host> </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
# 암호군 목록(비파괴)
nmap -Pn -p 443 --script ssl-enum-ciphers <host>
# 응답 헤더
curl -sI https://<host>/
curl -sI http://<host>/      # HTTPS로 넘기는가
```

점검 포인트:
- TLS 1.2 이상만. 인증서 체인 완전, 이름 일치, 만료 여유, 자동 갱신 여부.
- HTTP는 HTTPS로 영구 이동(301/308).
- `Strict-Transport-Security`(충분한 `max-age`), `X-Content-Type-Options: nosniff`, 프레임 보호(`Content-Security-Policy: frame-ancestors` 또는 `X-Frame-Options`), `Content-Security-Policy`.
- `Server`·`X-Powered-By` 같은 헤더가 버전을 흘리지 않는가.

### 2.3 애플리케이션 면

읽기 요청만, 점검용 계정(인가에 포함된 것)으로만.

```bash
# 민감 엔드포인트: 자격 없이 부르면 401/403이어야 한다
curl -s -o /dev/null -w '%{http_code}\n' https://<host>/<path>
# CORS: 임의 출처를 반사하면서 자격증명을 허용하는가
curl -sI -H 'Origin: https://example.invalid' https://<host>/<path> \
  | grep -i '^access-control-allow'
# 운영 환경의 자동 생성 API 문서·스키마
for p in <docs-path-1> <docs-path-2> <schema-path>; do
  curl -s -o /dev/null -w "%{http_code} $p\n" https://<host>/$p
done
```

점검 포인트:
- **인증 강제**: 목록·상세·관리·내보내기·파일 내려받기 엔드포인트가 자격 없이 200을 주지 않는가. 프레임워크의 기본 관리 화면 경로가 바깥에 열려 있지 않은가.
- **IDOR**: 점검용 계정 둘(A·B)을 받아, A의 자격으로 B 소유 객체의 식별자를 읽기 요청해 거부되는지 본다. 남의 실제 데이터를 열어 보는 시도는 하지 않는다 — 인가 받은 시험 계정끼리만.
- **CORS**: `Access-Control-Allow-Origin`이 요청 출처를 그대로 반사하거나 `null`을 허용하면서 `Access-Control-Allow-Credentials: true`이면 위험. 허용 출처는 고정 목록이어야 한다.
- **운영 API 문서**: Swagger UI·ReDoc·OpenAPI/GraphQL 스키마 같은 자동 생성 문서가 운영에서 인증 없이 열려 있으면 공격 면 지도를 그대로 주는 셈이다. 운영에서는 끄거나 인증 뒤로 둔다. 프레임워크마다 기본 경로가 다르니 쓰는 프레임워크의 문서에서 기본 경로를 확인해 대입한다.
- 오류 응답이 스택 추적·내부 경로·설정값을 흘리지 않는가(디버그 모드 꺼짐).

## 3. 심층 방어 — 같은 포트를 두 층에서 막는다

바깥에 열리면 안 되는 포트는 **두 층**에서 막는다. 한 층이 실수로 열려도 다른 층이 막는다.

| 층 | 무엇 | 예 |
|---|---|---|
| 바깥층 | 클라우드 방화벽이 외부 유입을 거부 | 보안목록·보안그룹·VPC 방화벽에서 그 포트의 공개 허용 규칙 제거 → `reference/clouds.md` |
| 안층 | 프로세스가 외부 인터페이스에 아예 묶이지 않음 | 컨테이너 포트를 모든 인터페이스가 아니라 호스트 내부 주소(루프백이나 컨테이너 브리지 게이트웨이)에만 게시 |

안층 예(일반 꼴):

```yaml
# compose: 모든 인터페이스에 게시 — 바깥층 하나에만 기댄다
ports: ["<port>:<port>"]
# 호스트 내부 주소에만 게시 — 방화벽이 열려도 바깥에서 닿지 않는다
ports: ["127.0.0.1:<port>:<port>"]
# 같은 호스트의 다른 컨테이너만 쓰면 게시하지 말고 내부 네트워크로만 잇는다
```

- 컨테이너 런타임의 포트 게시는 호스트 방화벽(iptables·ufw 등) 규칙을 앞지르는 경우가 있다. 호스트 방화벽만 믿지 말고 바인딩 주소를 직접 확인한다: `ss -ltnp`에서 `0.0.0.0`·`[::]`로 듣는 것을 찾는다.
- 다른 호스트가 써야 하는 포트(사설망의 DB 등)는 사설 인터페이스 주소에만 묶고, 바깥층에서 사설 대역만 허용한다.

**폐곡선**: 점검 → 조치 → **2단계와 같은 두 지점에서 다시 외부 스캔** → 표에 「조치 후」 칸을 채운다. 설정 파일을 읽어 「막혔을 것」이라고 판정하지 않는다 — 바깥에서 잰 결과만 판정 근거다.

## 4. 사고 교훈 — 방화벽을 좁힐 때

- **사설 대역 허용을 먼저 남긴다.** 클라우드 방화벽 규칙은 흔히 외부 유입뿐 아니라 **같은 사설망 안 호스트끼리의 통신**까지 함께 다스린다. DB·캐시가 같은 호스트가 아니라 사설망의 다른 호스트에 있을 수 있다. 공개 허용을 지우기 **전에** 사설 대역(`<cidr>`) 허용 규칙이 있는지 확인하고 없으면 먼저 넣는다.
- 바꾸기 전 규칙을 통째로 기록해 둔다(되돌리기용). 한 번에 규칙 하나씩 바꾸고, 바꿀 때마다 서비스 건강 확인과 외부 재스캔을 한다.
- **서비스가 죽으면 재시작부터 하지 않는다.** 먼저 의존(DB·캐시·큐)까지의 네트워크 경로를 의심한다: 앱 호스트에서 `nc -zv -w 3 <db-host> <port>`, 앱 로그의 연결 시간 초과·거부 메시지. 방금 바꾼 규칙이 원인이면 재시작은 아무것도 고치지 못하고 시간만 쓴다.
- 조치가 끝나면 무엇을 바꿨는지(규칙 전후·바인딩 전후·재스캔 결과)를 비공개 점검 기록에 남긴다.
